### From Routing Checks to Trajectory Testing: Evaluating an Agentic Chatbot - (Python Weekly)

https://edcrewe.blogspot.com/2026/08/from-routing-checks-to-trajectory.html

# Summary

This article chronicles the evolution of a testing framework for an agentic AI chatbot built for Postgres AI Hybrid Manager. The author traces the progression from simple routing tests (verifying the chatbot selects the correct tool) through Task Completion Rate (TCR) evaluations that assess overall response quality using LLM-as-judge scoring against rubrics, to handling multi-turn conversations. A key insight is distinguishing between "direct mode" testing (which evaluates the model's capability in isolation) and "proxy mode" testing (which exercises the full production system with real tools, routing, and conversation state).

The core challenge is that unlike deterministic APIs, agentic chatbots can sound confident while producing incorrect results through wrong tool selection, incomplete task completion, or poor information handling. The framework solves this through "trajectory testing"—validating not just that the chatbot returns a plausible answer, but that it follows the correct path of tool calls and reasoning steps to arrive at that answer. Multi-turn conversations further complicated the testing by requiring conversation state preservation across both execution modes, demonstrating that effective agentic AI testing requires end-to-end validation of the entire deployed system, not just the underlying language model.

### Prototype on a laptop, scale to 16 billion rows: one Polars query - (Python Weekly)

https://pola.rs/posts/market-data-to-plotly-enterprise-dashboard/

# Summary

Polars enables data teams to prototype on a laptop and scale to massive datasets without rewriting code. The article demonstrates this by taking a subset of Polymarket orderbook data (97 million rows from 3 hours) to explore locally, then running the identical Polars queries on the full month (16 billion rows, 500 GB) on Polars Cloud. ### Model Genome: Fingerprinting Whether an LLM Was Trained From Scratch or Derived - (Python Weekly)

https://huggingface.co/blog/mayafree/model-dna

# Summary

This article presents a method for determining whether a large language model was trained from scratch or derived from an existing open-weight base model. The authors developed a three-axis fingerprinting system: (1) **Architecture fingerprint** comparing config.json parameters like hidden size and layer count, (2) **Tokenizer fingerprint** measuring vocabulary overlap between models, and (3) **Weights fingerprint** using Linear CKA to detect embedding similarity. They discovered important limitations—row-wise cosine similarity is useless due to rotational invariance, and CKA struggles to distinguish continued pretraining from independent training—making the config and tokenizer the most reliable evidence.

The authors applied this reproducible pipeline to nine Korean organizations' foundation models, creating a "genotype" classification system ranging from Native (fully self-developed) to Ported (exact architecture and tokenizer match). They emphasize that using open-weight bases is legitimate industry practice, and their tool simply reports lineage objectively without assigning wrongdoing. The method is transparent, reproducible, and available as a live demo on Hugging Face Spaces.

### python string literals are kinda funny - (Python Weekly)

https://sebsite.pw/w/20260806-pystrings.html

# Summary

Python's string literal syntax contains quirky edge cases stemming from implementation simplifications. Raw string literals (prefixed with `r`) cannot end in a backslash because backslash escapes aren't interpreted, yet the lexer still processes quotes the same way as regular strings—so a backslash before the closing quote prevents the string from terminating properly.

F-strings introduce even more complexity since they require a full Python parser to handle expressions inside curly braces, which can contain quotes, comments, and span multiple lines. The expression terminates only at an unparenthesized `}`, `!`, or `:`, leading to amusing restrictions: lambda expressions and assignment expressions must be parenthesized within f-strings, otherwise the `:` or `:=` operators will prematurely end the expression parsing.

### Python: introducing emojet, a fast emoji lookup library - (Python Weekly)

https://adamj.eu/tech/2026/08/12/python-introducing-emojet/

# Summary

Adam Johnson introduces **emojet**, a new Python library for fast emoji-to-name conversion and vice versa. Built as a Rust extension module, emojet provides the same API as the popular `emoji` package but offers dramatic performance improvements: 3.5x faster for emojize() conversion, 70x faster for demojize() conversion, and uses 40% less memory. The library supports 14 languages plus GitHub/Slack aliases and was developed to optimize startup times for Johnson's client Rippling.

All emoji data is baked into the binary format and shared between processes via the operating system's page cache, reducing the import time from 20.57ms to just 869.94 microseconds compared to the original emoji package.

### Two lines of Python that segfault the interpreter - (Python Weekly)

https://deadlovelll.github.io/2026-08-10-conditional-annotations-set-add-crash/

# Summary

This article describes a critical bug in CPython 3.14-3.16 where just two lines of Python code could crash the interpreter without a traceback. The vulnerability exploited PEP 749's lazy annotation evaluation feature, which introduced a `__conditional_annotations__` global set to track which conditional annotations were actually executed. Since this was an ordinary global variable, user code could reassign it to a non-set value, causing the `SET_ADD` opcode to perform unchecked type casting and read garbage memory, resulting in a segfault.

The root cause was that `SET_ADD` was originally designed for set comprehensions where the set operand was unreachable from Python code, so no type checking was needed. When PEP 749 reused this opcode for annotations by loading the set via a global variable name, it violated that hidden invariant. The fix differed by branch: the development version added a dedicated, type-checking intrinsic for conditional annotations, while released versions 3.14 and 3.15 received a simpler defensive guard on `SET_ADD` itself. This illustrates how compiler assumptions must be explicitly documented when code is reused in new contexts.

### A quick look at zero-knowledge proofs - (Python Weekly)

https://bernsteinbear.com/blog/zkp/

# Summary

Zero-knowledge proofs (ZKPs) allow a prover to convince a verifier of a solution to a problem without revealing the actual solution. The article uses 3-coloring a graph—assigning colors to nodes so no adjacent nodes share the same color—as a canonical example. The prover commits to a valid 3-coloring by permuting the colors and hashing them into "locked boxes," then selectively reveals only the colors of edges the verifier randomly requests, proving the coloring is valid without exposing the complete solution.

The protocol works through an iterative process repeated many times (m² iterations, where m is the number of edges). In each iteration, the prover hashes a permuted coloring with nonces for security, the verifier randomly selects an edge to inspect, the prover reveals the colors and nonces for that edge's endpoints, and the verifier verifies the hash values match and the colors differ. This approach provides security because the prover cannot predict which edge will be requested, and the colors are reshuffled each round, preventing the verifier from accumulating information about the actual coloring across iterations.

### Numba in the Browser: Unlocking a New Scientific Python Stack in JupyterLite - (Python Weekly)

https://notebook.link/blog/numba-in-the-browser/

# Summary

JupyterLite, which runs Python kernels in the browser via WebAssembly, has been missing a crucial component: the Numba JIT compiler. Researchers at QuantStack have now successfully brought Numba to the browser by developing a WebAssembly-aware execution engine for llvmlite (Numba's LLVM binding layer). This involved creating a custom pipeline that compiles LLVM intermediate representations to WebAssembly objects, links them using LLVM's LLD linker in-process, and dynamically loads them as side modules—all without requiring a remote server. The result delivers approximately 250× speedup over standard Python in browser environments.

With Numba now packaged and available through emscripten-forge, an entire ecosystem of scientific Python libraries becomes accessible in JupyterLite. This includes downstream packages like PyTensor, PyMC, and Dolo.py that depend on Numba or similar compilation backends for numerical computing and probabilistic modeling. This breakthrough transforms JupyterLite from a lightweight Python environment into a platform capable of serious compiled scientific computing directly in the browser, enabling scalable sharing of interactive computational notebooks for education, documentation, and scientific research without server infrastructure.

### Introducing Flex: Let the Model Write the Code - (Python Weekly)

https://www.cmpnd.ai/blog/let-the-model-write-the-code.html

# Summary

Flex is a new DSPy module that allows AI models to optimize not just the prompts and instructions of programs, but the actual code itself. Unlike previous optimizers that rewrote instructions, Flex exposes program code to the optimizer, enabling models to decompose tasks, write helper functions, and implement routing logic. The generated code executes in a sandbox for security, with only model calls and explicit tools bridging back to the host process.

In a geospatial conflation task (determining if two place listings refer to the same location), Flex with GEPA optimization achieved 95% accuracy while being 28% cheaper and 40% faster than the baseline. By penalizing model calls in the optimization metric, the system intelligently routed 75% of cases to deterministic Python rules, reserving expensive LLM calls only for genuinely ambiguous cases. At higher penalties, the system maintained baseline accuracy using 1/30th the latency and 1/100th the cost, demonstrating that code-level optimization can dramatically improve both performance and efficiency.
