### Bringing PyTorch Monarch to AMD GPUs: Single-Controller Distributed Training on ROCm - (Python Weekly)

https://pytorch.org/blog/bringing-pytorch-monarch-to-amd-gpus-single-controller-distributed-training-on-rocm/

# Summary

PyTorch Monarch has been successfully ported to AMD Instinct GPUs with ROCm, enabling fault-tolerant distributed training at scale. The port required significant engineering effort to adapt Monarch's GPU runtime and communication stack from CUDA to ROCm, including converting collective communications using hipify_torch, adapting GPU memory management, and reconfiguring RDMA integration. The implementation uses a compatibility shim approach in Rust to maintain platform-agnostic code rather than introducing platform-specific branches throughout the codebase.

The key innovation is Monarch's ability to enable elastic, fault-tolerant training without relying on traditional checkpoint-restart approaches. When failures occur during training, healthy nodes continue operating while failed nodes are dynamically restarted and rejoin the cluster through peer checkpoint transfers, minimizing wasted computation and cluster idle time. This hierarchical fault-handling model, demonstrated through integration with TorchTitan and TorchFT, represents a significant advancement toward stable, large-scale AI infrastructure that can reliably train multi-billion parameter models across thousands of GPUs.

### The Design of Everyday Cryptography - (Python Weekly)

https://www.dlp.rip/everyday-cryptography/

# Summary

This article examines why cryptographic interfaces vary dramatically in usability, comparing the elegant simplicity of Key Encapsulation Mechanisms (KEMs) with the complexity of modern digital signatures. KEMs succeed because they use an indirect approach—generating a fixed-size shared secret that users pass to symmetric encryption without needing to make decisions about what gets encrypted. Digital signatures, by contrast, are "micro-managers" that require users to navigate multiple decisions: whether to use pure or prehashed variants, which hash algorithm to choose, and how to handle context strings. This complexity grew from attempts to provide security benefits like collision-resistance independence and domain separation, but it makes these interfaces difficult and error-prone to use safely.

The author proposes that signatures could become more usable by adopting a KEM-like approach: defining signatures over fixed-size message representatives instead of arbitrary-length messages. A separate protocol would handle the computation of these representatives, incorporating context, randomness, and other parameters through a standard construction. This indirection would shift complexity away from the cryptographic interface itself, allowing signatures to be simpler and more difficult to misuse—demonstrating a broader principle that well-designed cryptographic interfaces should be opinionated and avoid unnecessary configuration options.

### Running subprocesses in Python - (Python Weekly)

https://www.pythonmorsels.com/running-subprocesses-in-python/

# Summary

Python's `subprocess.run()` function allows you to launch and control external programs from within Python. The function takes a list of command-line arguments, with options to capture output (using `capture_output=True`), decode it as text (using `text=True`), and check for errors (using `check=True`). By default, subprocess output appears in the terminal, but you can capture it and access it through the returned `CompletedProcess` object's `stdout` and `stderr` attributes.

To handle errors effectively, you can check the subprocess's `returncode` attribute (0 indicates success) or use `check=True` to automatically raise a `CalledProcessError` exception on failure. For cleaner code when running multiple subprocesses with the same options, you can create a custom wrapper function that applies default arguments like `capture_output=True`, `text=True`, and `check=True` to all subprocess calls.

### Pip 26.2: –only-deps solves 16 years of app deployment hacks - (Python Weekly)

https://jamesoclaire.com/2026/07/23/pip-26-2-only-deps-solves-16-years-of-app-deployment-hacks/

# Summary

Pip 26.2 is introducing a new `--only-deps` flag that finally solves a 16-year problem in Python deployment: installing project dependencies from `pyproject.toml` without installing the package itself. The command `pip install --only-deps .` addresses a long-standing pain point for application backends, scripts, and REST APIs that aren't meant to be installed as packages, eliminating years of workarounds like manually editing requirements.txt files or using editable installs.

This solution emerged from a decade of community effort, including the standardization of `pyproject.toml`, PEP 517 build hooks, and the popularity of alternative tools like `uv` that demonstrated real demand for this functionality. After numerous failed attempts and discussions spanning 16 years, Sebastian Höffner's PR #13895 finally brings this elegant solution to pip, making it available in July 2026.
