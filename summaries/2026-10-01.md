https://www.infoq.com/news/2026/10/software-engineering-skills/

# Summary

Software engineers must intentionally slow down to develop skills effectively, as AI tools accelerate outcomes but don't necessarily support learning. ### Article: High Availability Is Not Resilience: Why Cloud Systems Fail When It Matters Most - (InfoQ)

https://www.infoq.com/articles/high-availability-not-resilience-cloud/

# Summary

The article distinguishes between high availability and resilience in cloud systems, arguing that they are fundamentally different concepts often confused in practice. High availability focuses on surviving *expected* failures with minimal interruption through redundancy and failover mechanisms, while resilience is the ability to recover from *unexpected* failures that systems weren't explicitly designed to handle. The author illustrates this with a real case where a compliance upgrade to TLS 1.3 inadvertently broke Route 53 health checks (which require TLS 1.2), causing the system to appear healthy internally but become invisible to traffic routing—a control-plane failure that high-availability architecture didn't account for.

The article emphasizes that achieving true resilience requires more than just architectural redundancy; it demands explicit ownership, continuous testing of recovery procedures, and identification of hidden dependencies across control planes (like DNS, identity management, and routing). The author notes that meaningful resilience testing is often prohibitively expensive or risky, leading organizations toward "performative resilience" where recovery is assumed rather than demonstrated, and that in complex distributed systems, resilience remains probabilistic rather than guaranteed.

### Cursor Uses S3 WAL to Scale Git Storage to More than 300 Pushes per Second - (InfoQ)

https://www.infoq.com/news/2026/09/cursor-continuity-git-storage/

# Summary

Cursor has developed Continuity, a new Git storage architecture that uses an S3-backed write-ahead log (WAL) as the authoritative source of truth instead of coordinating multiple replicas. Local NVMe repositories function as warm caches rather than authoritative copies, with pushed data persisted to S3 before acknowledgment. This approach achieves linear read scaling with up to 100 replicas and supports over 300 pushes per second using S3 Express One Zone.

The architecture shifts the consistency boundary from the replica layer to durable object storage, trading replica coordination for storage validation and asynchronous propagation. Cursor reports that repositories can be materialized on-demand from the WAL when needed, and only the primary performs Git compaction with replicas downloading resulting packs from S3. This design particularly benefits large monorepos with heavy CI workloads and the proliferation of smaller repositories created by coding agents, though the published performance figures have not been independently verified.

### Cloudflare Adds Configurable HTTP Vary Header Support to Prevent Cache Thrashing - (InfoQ)

https://www.infoq.com/news/2026/09/cloudflare-http-vary/

# Summary

Cloudflare has introduced configurable HTTP Vary header support across its global edge network to address cache fragmentation issues. The HTTP Vary header tells caches which request headers influence a response, but without proper management, minor variations in client headers (whitespace, casing, language preferences) can create dozens of cache variants, causing "cache thrashing" where cache hit ratios collapse and origin server load increases. Cloudflare's analysis found that nearly 3,000 origins varied on four or more request headers, with some varying across dozens of fields.

To solve this, Cloudflare decoupled header negotiation into two stages: origin servers continue specifying which headers matter, while Cloudflare's Cache Rules now dictate how the edge normalizes or processes those headers before caching. Operators can choose from three actions per header—normalize (canonicalize complex headers into standard equivalents), pass through (store exact strings), or bypass (skip caching for volatile headers)—preventing unnecessary cache fragmentation while maintaining correctness. This eliminates the need for manual workarounds and specialized configurations.

https://www.oreilly.com/radar/a-data-center-is-a-dependency-graph-before-it-is-a-building/

# Summary

This article argues that bringing a hyperscale data center region into production is fundamentally a software coordination challenge, not a construction problem. While the physical infrastructure—power, cooling, networking, and hardware—can be completed on schedule, the actual transition to production readiness depends entirely on successfully bringing hundreds of interdependent services online in the correct order. This process typically takes 6-12 months after physical completion and carries significant schedule risk.

The key to managing this transition is understanding and managing the dependency graph—a map showing which services must be running before others can start. The article emphasizes that while individual platform teams typically track their own milestones, what's often missing is end-to-end ownership of the complete dependency graph across all teams. Without this holistic view, teams can report individual progress while the region remains blocked at the system level. Successful region launches require coordinated mapping of all service dependencies, careful sequencing, and continuous tracking of what's blocking the startup sequence as plans inevitably change.

### From Raw Data to Graph-Native AI - (Radar)

https://www.oreilly.com/radar/from-raw-data-to-graph-native-ai/

# Summary

This article discusses "graph-native AI," an approach that emphasizes the often-overlooked step of converting raw data into meaningful graph structures before applying machine learning techniques. The author argues that while discussions of AI focus heavily on graph neural networks, GraphRAG, and foundation models, insufficient attention is paid to the critical upstream work of graph modeling—deciding what entities and relationships should exist, how time is represented, and how conflicting data should be resolved.

The key insight is that graph modeling should be treated as a first-class stage in AI development, creating a shared graph representation that can support multiple downstream applications (queries, predictions, retrieval, agents). The author illustrates this with a customer-support example, noting there is no single "correct" way to model data—choices depend on business objectives (e.g., entity graphs for relationships, event graphs for temporal analysis, evidence graphs for provenance). The article challenges the assumption that database schemas designed for storage and transactions automatically work well for machine learning, positioning thoughtful graph design as foundational to effective AI systems.
