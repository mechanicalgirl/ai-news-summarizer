### What's missing to have reproducible builds on PyPI - (Python Weekly)

https://snarky.ca/whats-missing-to-have-reproducible-builds-on-pypi/

# Summary

Reproducible builds on PyPI would enhance supply chain security by allowing independent verification that distributed packages match their source code and haven't been tampered with during the build process. Currently, Python packaging lacks the necessary infrastructure: source code location and software bill of materials (SBOMs) aren't recorded in distributions, sdists lack a structured metadata format to store this information, and there's no mechanism for trusted verifiers to signal successful reproduction to users.

To enable reproducible builds, the author proposes: recording source code locations in distribution metadata, implementing SBOMs for sdists (possibly through a new sdist v2 format), leveraging the existing `pyproject.toml` build-system entry point to replay builds with recorded dependencies, and creating a system where trusted organizations can verify distributions and provide feedback to PyPI. Importantly, this should be positioned as an optional benefit rather than a requirement, allowing producers to opt in without extra effort while giving security-conscious users visibility into which packages have been independently verified.

### When str.lower() is a security vulnerability in Python - (Python Weekly)

https://sethmlarson.dev/when-str-lower-is-a-security-vulnerability

# Summary

This article explains how Python's `str.lower()` function can create a security vulnerability in IDNA (Internationalized Domain Names in Applications) implementations. The StringPrep algorithm used in IDNA 2003 depends on Unicode 3.2.0 case-folding rules as specified in RFC 3454, but Python's `str.lower()` uses whatever Unicode version the interpreter was compiled with (often much newer). This discrepancy causes domain names to be encoded differently than the specification requires, potentially creating security inconsistencies.

The fix involved creating exception mappings for specific Unicode codepoints where `str.lower()` behaves differently between the current Unicode version and Unicode 3.2.0, ensuring IDNA 2003 compliance with the RFC specification. This highlights how using a function that appears correct on the surface can introduce subtle but important vulnerabilities when standard compliance depends on specific versioning.

### From P-Code to GNN: extract binary code semantics - (Python Weekly)

https://blog.quarkslab.com/from-p-code-to-gnn-extract-binary-code-semantics.html

# Summary

Quarkslab has released **pcode_graph**, a Python library that extracts semantic graphs from binary code to enable machine learning-based function similarity detection. The library uses Ghidra's P-Code intermediate representation (limited to 63 opcodes) rather than architecture-specific assembly, making it resilient to compiler optimizations and architectural differences. By converting binary code into Control & Data Flow Graphs (CDG), the tool abstracts away implementation details while preserving semantic meaning, allowing neural networks to recognize functionally identical code regardless of how it was compiled.

The approach addresses key limitations of statistical feature extraction (which fails when the same logic is compiled differently) by building graphs that remain stable under instruction reordering and optimization variations. The article demonstrates the methodology using the Cisco-Talos dataset, with pcode_graph processing the extracted graphs through data flow analysis passes before feeding them into Graph Neural Networks (GNNs) for training. This semantic graph approach is more robust than simpler methods and supports various binary analysis use cases including vulnerability detection, deobfuscation, function identification, and malware classification.

### What Is Reasoning - (Armin Ronacher's Thoughts and Writings)

https://lucumr.pocoo.org/2026/8/19/what-is-reasoning/

# Summary

Armin Ronacher explains how AI models handle "reasoning traces"—the internal thinking processes that models perform before generating final answers. He clarifies that reasoning traces are simply text generated by models trained to emit their thinking into a separate channel before showing users the final answer. For open-weight models, these traces are visible; for closed models, they're typically hidden or redacted. The "reasoning effort" level (low, medium, maximum) is controlled through system prompts rather than being a special sampling property, which explains why changing it invalidates the cached data.

Ronacher also discusses how reasoning can be manipulated or "leaked" from models. When reasoning is disabled, models may sometimes be tricked into outputting their internal thinking in unexpected places (like custom tools) because the thinking channel is merely a learned convention rather than a hard technical constraint. Ultimately, he argues that the special aspect of reasoning features comes down to training models to keep scratch work separate from final answers, and the separation can be circumvented if models are confused about which channel they should be writing to.
