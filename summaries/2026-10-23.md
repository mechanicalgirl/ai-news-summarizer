### Python's binary wheels and supply chain attacks - (Python Weekly)

https://rushter.com/blog/python-binary-wheels/

# Summary

Python's package distribution system relies on "wheels"—precompiled binary files that make installing packages faster and easier than compiling from source. However, this convenience creates a significant security vulnerability: attackers can upload malicious binaries alongside clean source code, and there's no mandatory way to verify that binaries were actually compiled from the published source code. This makes binary wheels a weak point in Python's ecosystem security.

The problem is compounded by the fact that malware scanners primarily focus on analyzing source code rather than binaries, which are much harder to reverse-engineer and detect for malicious behavior. Attackers could embed subtle implants in binaries that trigger after extended periods, evading detection for weeks. The author predicts such supply chain attacks will become increasingly common and suggests the only practical mitigation is to compile all Python dependencies from scratch rather than relying on pre-built wheels.

### LiteLLM Hijacked Again: Malicious 1.107.0 Wheels Steal Credentials and Load Remote Code - (Python Weekly)

https://research.jfrog.com/post/litellm-hijacked-again/

# Summary

JFrog Security Research discovered malicious code in litellm version 1.107.0, a popular Python interface for large language model providers. The compromised wheels contained three additional files (cook.pth, cook.py, and sitecustomize.py) that execute at Python startup to steal credentials and secrets, and establish hourly remote-code execution channels—even when applications never directly import litellm. All seven PyPI wheels across different platforms were affected, along with the official Docker image, though PyPI and Docker Hub have since removed the compromised releases.

This represents the second hijacking of LiteLLM in 2026, and is particularly notable because the malicious payload only appeared in the compiled wheel binaries, not in the published source code. The injected files use Python startup hooks to trigger a credential stealer called "privcollect" that targets an extensive array of sensitive data, including SSH keys, cloud credentials, AI development configs, CI/CD secrets, and LiteLLM proxy databases. The stolen data is encrypted and exfiltrated to a look-alike domain, highlighting how attackers can compromise projects at the build artifact level, bypassing source code review.

### How to Run Turing-Complete Malware in PyTorch's Backward Pass - (Python Weekly)

https://elonlit.com/scrivings/how-to-run-turing-complete-malware-in-pytorchs-backward-pass/

# Summary

This article describes a critical security vulnerability in PyTorch where attackers can execute arbitrary Turing-complete programs during the backward pass of neural network training by exploiting a disagreement between IEEE 754 floating-point arithmetic and symbolic differentiation. A malicious loss function can evaluate to exactly 0.0 in the forward pass (appearing legitimate in training metrics) while still forcing the optimizer to execute an attacker-controlled program through carefully crafted gradients. The vulnerability works because the GPU's floating-point rounding behavior differs from PyTorch's autograd engine's symbolic math calculations.

The author demonstrates this vulnerability by showing how to implement Conway's Game of Life within a neural network's weights. By leveraging floating-point precision limits at scale 2³⁰ (where float32 can only represent multiples of 128), they create a function that appears as zero to the GPU but maintains gradient information in PyTorch's computation graph. Using the product rule as a "gradient multiplexer," the attack multiplies a detached target gradient vector by zeroed weights, resulting in zero loss during training while the backward pass correctly computes arbitrary state transitions. This represents a severe supply-chain attack risk for fine-tuning open-source models with untrusted regularization functions.

### Comprehensive Tutorial on Django ORM, Migrations and makemigrations - (Python Weekly)

https://my-space.io/blog/django-orm-migrations/

# Summary

Django's ORM (Object-Relational Mapper) allows developers to work with databases using Python classes instead of SQL. The migration workflow follows a simple three-step loop: define or change a model in Python, run `makemigrations` to generate a migration file documenting the change, and then run `migrate` to apply that file to the database. The key distinction is that `makemigrations` only writes files and never touches the database, while `migrate` actually applies those changes and records them in Django's `django_migrations` table.

The article emphasizes that most Django migration problems stem from misunderstanding these separate steps or allowing the migration files and database state to fall out of sync. It provides a practical tutorial building a coffee and tea store example to demonstrate common scenarios like backfilling required fields, rolling back migrations, and resolving migration conflicts between team members, with the goal of helping developers move beyond common beginner mistakes like deleting database files when errors occur.

### How to Build a Decision Model Like Jev - (Python Weekly)

https://www.fratepietro.com/2026/how-to-build-a-decision-model-like-jev/

# Summary

This article explains how to build decision models—specialized LLMs optimized for classification tasks rather than text generation. The author argues that most real-world applications (routing support tickets, scoring rubrics, flagging risky actions) don't need full text generation and instead benefit from probability distributions over known outcomes. TypeSafe's Jev framework introduced a typed contract for this via `/v1/systemone`, which now has open-source support in Hugging Face's transformers library, allowing developers to turn 250+ existing LLM architectures into efficient decision models.

The article provides a practical implementation roadmap: starting with zero-shot inference on existing models, then advancing through three key improvements. These include introducing reserved option tokens (`<opt_0>` through `<opt_254>`) with a dedicated readout head to handle up to 255 options and eliminate positional bias, implementing probability calibration through temperature scaling and ranked penalty functions to ensure reported probabilities match actual accuracy, and optimizing for inference efficiency through batching and quantization. The result is that open-weight decision models like SemIf now compete with proprietary Jev at roughly half the cost per decision.

### Introducing TorchTPU - (Python Weekly)

https://pytorch.org/blog/introducing-torchtpu/

# Summary

TorchTPU is a new open-source collaboration between Google and Meta that provides a native PyTorch backend for Google TPUs, enabling seamless execution of PyTorch models on TPU hardware with minimal code changes (e.g., simply changing `.to("cuda")` to `.to("tpu")`). Unlike previous efforts like PyTorch/XLA that relied on lazy tensor compilation and JAX integration, TorchTPU prioritizes eager execution, full PyTorch ecosystem compatibility, and support for distributed computing primitives like DDP and FSDP.

The project, launched in mid-2025 and already used in production by major Google Cloud customers, supports approximately 450 ATen operations and validates compatibility with thousands of models from Hugging Face across LLMs, vision, audio, and NLP domains. TorchTPU offers both eager and compiled execution modes (including a new DeferAndFuse mode) and integrates with popular frameworks like vLLM, TorchTitan, and Ray, aiming to deliver competitive performance to PyTorch on GPUs for large-scale training and inference workloads.
