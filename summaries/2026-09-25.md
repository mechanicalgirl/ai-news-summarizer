### Share how you use Django with Django Probe - (Python Weekly)

https://www.better-simple.com/django/2026/09/17/share-how-you-use-django-with-django-probe/

# Summary

Django Probe is a new package that allows Django projects to anonymously share how they use Django—tracking which decorators, classes, methods, and functions they employ—so the community and framework maintainers can make better, data-driven decisions. Created by Tim Schilling after pitching the idea at DjangoCon US, the tool works as a simple linter that scans code and submits usage patterns to a central hub, enabling insights into deprecation decisions, feature prioritization, and community documentation needs.

Currently in active development with 11 early adopters, Django Probe has potential to transform how Django evolves by replacing gut-feeling decisions with objective usage analytics. While the package currently only accepts data without yet providing analysis dashboards, it could eventually help answer critical questions—like whether deprecated features like `QuerySet.extra()` are still in use, or whether features like MFA should be built into Django's auth system. The project welcomes both new users sharing their project data and contributors helping develop reporting features.

### Fighting for #1 in the Ultimate Tic-Tac-Toe Arena - (Python Weekly)

https://tomalard.github.io/posts/fighting-for-1-in-the-ultimate-tic-tac-toe-arena/

# Summary

Ultimate Tic-Tac-Toe (UTTT) is a competitive bot programming arena on CodinGame where players code AI opponents to play a 3×3 grid variant of tic-tac-toe. The competition imposes strict constraints—100k character limit, single vCPU, and 100ms per turn—that actually level the playing field by preventing competitors from using massive neural networks or opening books trained on expensive hardware, allowing solo developers with consumer PCs to compete at the highest level.

To dominate the leaderboard, top competitors like the author use Efficiently Updatable Neural Networks (NNUEs)—a technique borrowed from chess programming—to evaluate board positions far better than simple heuristics. The author's winning submission uses a sophisticated (189→1024)×2→10 NNUE trained on 300+ million self-play positions, which is smuggled into the character limit by encoding a compiled C binary as compressed Unicode characters executed through a Python wrapper, bypassing Python's inherent slowness.

### Hardware-Agnostic Models in vLLM - (Python Weekly)

https://pytorch.org/blog/hardware-agnostic-models-in-vllm/

# Summary

vLLM is introducing "hardware-agnostic" layers to address a critical challenge: as frontier models increasingly require custom, hardware-specific optimizations that break compatibility with torch.compile, vLLM risks leaving behind users with older GPUs, out-of-tree accelerators, and exotic models. The new layers will maintain full-graph torch.compile support and extensibility mechanisms while remaining isolated from hardware-specific implementations, allowing vLLM to pursue aggressive performance optimizations for cutting-edge GPUs without abandoning its broader user base.

The solution creates a dual-path architecture where hardware-agnostic layers (built with native PyTorch, Triton, and Helion for portability) coexist alongside hardware-specific "flat" model definitions. On NVIDIA H100 GPUs, the hardware-agnostic layers achieve within 3.4% of native performance while maintaining compatibility across diverse hardware platforms, ensuring vLLM can simultaneously serve both frontier performance needs and users dependent on older or alternative accelerators.

### Put the Arithmetic in the Tool: an MCP Server for an AWS Waste Scanner - (Python Weekly)

https://dev.to/aws-builders/put-the-arithmetic-in-the-tool-an-mcp-server-for-an-aws-waste-scanner-3n79

# Summary

This article presents a guide for building an MCP (Model Context Protocol) server that integrates an AWS cost scanner with AI agents. The author emphasizes a critical principle: rather than returning raw data rows for AI models to process, the server should return pre-computed totals, breakdowns, and answers to common questions (counts, costs, minimums, maximums). This approach is necessary because AI models frequently make arithmetic errors when asked to sum multiple values—testing showed one model failed basic addition on just eleven items 20 out of 20 times.

The implementation includes seven practical steps: scanning AWS resources from the terminal, exposing the same engine via an MCP stdio interface, returning computed figures instead of rows, echoing filters back with results for verification, keeping all tools read-only, ensuring totals match the sum of individual rows (accounting for rounding), and calibrating estimates against actual AWS billing data. The author also demonstrates how to deploy this as a Claude Code plugin, while maintaining safety by preventing the MCP server from executing destructive operations—cleanup actions remain exclusive to terminal commands where per-resource prompts protect against mistakes.

### Bad evals, my own: five exercises from two LLM judges - (Python Weekly)

https://digline.dev/blog/bad-evals-my-own/

# Summary

The author runs two small LLM judges and discovered significant flaws in their evaluation methodology by applying Dan Luu's simple exercise framework: asking "what's wrong with this?" before providing explanations. Through five concrete exercises using actual data from their systems, they expose problems including non-deterministic outputs from identical configs, difficulty interpreting rule changes, incomplete ground truth data, conflicting metrics on different dataset sizes, and discontinuities in their evaluation gates.

The exercises reveal that LLM evaluation is fraught with subtle pitfalls—even when you built the system yourself and have access to all the data. The author's main finding is that proper evaluation requires rigorous thinking about what metrics actually measure, whether ground truth is truly complete, and how sample selection affects results, rather than simply trusting that automated systems with green gates are working correctly.

### Speeding Up a Python Service with CinderX: JIT and Static Typing - (Python Weekly)

https://dev.to/deadlovelll/speeding-up-a-python-service-with-cinderx-jit-and-static-typing-53bh

# Summary

**CinderX** is a CPython extension that accelerates Python services through Just-In-Time (JIT) compilation and static typing. It replaces CPython's frame evaluator with a more sophisticated compiler that converts Python bytecode into optimized machine code. Unlike CPython 3.14's tier 2 JIT, which compiles small code segments (UOPs), CinderX compiles entire functions as complete units, enabling better optimization through intermediate representations (HIR/LIR) in Static Assigned Form (SSA) with full type inference.

The article contrasts two compilation approaches: CPython's "copy-and-patch" method pre-compiles code stencils and patches them at runtime with minimal overhead, while CinderX performs deeper analysis and optimization including type checking, inlining, and redundancy elimination. CinderX leverages profiling data from CPython's adaptive interpreter to insert type guards, then optimizes aggressively based on these assumptions. The key insight is that performance improvements depend on the proportion of bytecode in your specific service—benchmarks on arithmetic kernels may not reflect real-world gains for database-driven applications.

### PyPy v8.0.0 - (Python Weekly)

https://pypy.org/posts/2026/09/pypy-v800-release.html

# PyPy v8.0.0 Release Summary

PyPy has released version 8.0.0, marking a major update that includes support for Python 2.7, 3.11, and 3.12 (beta). The major version bump was driven by infrastructure changes, particularly updating Linux builds to use glibc 2.28 based on AlmaLinux 8 with gcc14, requiring modern system libraries to run the compiled binaries.

A significant technical achievement in this release is cp312-abi3 support, which allows PyPy to use C-extension wheels built for CPython 3.12 using the limited ABI. This involved restructuring PyPy's C layer to hide internal implementation details while maintaining compatibility with CPython's headers, potentially making it easier for package developers to support PyPy. The release also includes improvements to RPython code generation (computed gotos and aggressive inlining), discontinuation of the HPy backend, and a revived tool for comparing header files between PyPy and CPython.
