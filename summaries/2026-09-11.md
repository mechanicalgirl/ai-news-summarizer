### Inside the megakernel serving engine for North Mini Code - (Python Weekly)

https://cohere.com/blog/megakernels

# Summary

Cohere has developed a specialized serving engine for their North Mini Code language model that uses a "megakernel" architecture—a single persistent GPU kernel that executes an entire forward pass instead of launching dozens of separate kernels sequentially. This approach reduces idle time and memory bandwidth waste, achieving 1.58× faster performance than the industry-standard vLLM on NVIDIA H100 GPUs, reaching 292 tokens/second at batch size 1 (62% of theoretical maximum speed versus vLLM's 39%).

The megakernel design addresses the fundamental bottleneck of LLM inference: memory bandwidth limitations rather than computational speed. By restructuring operations into a single CUDA kernel with explicit task scheduling and synchronization in global memory, Cohere eliminates the overhead of kernel launches, reduces GPU idle time (wave quantization), and improves data locality. The system maintains performance gains across various batch sizes and context lengths while supporting production features like continuous batching and paged attention, demonstrating that megakernels are practical for real-world serving infrastructure.

### Reading __dict__ once permanently deoptimizes attribute access - (Python Weekly)

https://deadlovelll.github.io/2026-09-05-reading-dict-deoptimizes-attribute-access/

# Summary

Since Python 3.11, attribute access no longer uses dictionary lookups but instead uses specialized opcodes that directly access an inline values array at a fixed byte offset—a much faster operation. However, reading an object's `__dict__` attribute even once permanently materializes it into a split-table dictionary, which deoptimizes all future attribute access on that object, increasing access time from ~8 nanoseconds to ~26 nanoseconds. This means casual operations like `vars(o)`, `copy.copy(o)`, or simply accessing `o.__dict__` can impose a lasting 3x performance penalty on all subsequent attribute operations for that object, making them far costlier than any gains from traditional optimization techniques like hoisting.

The article demonstrates this through benchmarking: an object with hoisted attribute access improves performance by 8ms, but simply materializing `__dict__` once adds an 18ms penalty that persists. The author notes this effect is even more pronounced in free-threaded Python (without the GIL), where atomic operations and reference counting add additional overhead, making attribute deoptimization a significant consideration in performance-critical code paths.

### Making a Python interpreter in 1024 bytes - (Python Weekly)

https://austinhenley.com/blog/python1024.html

# Summary

Austin Z. Henley successfully built a Python interpreter in 1024 bytes of C code as a weekend coding challenge. The interpreter uses a simple recursive descent parser that executes expressions on-the-fly rather than compiling to bytecode, with minimal state management relying on global variables and the C call stack. It supports a surprisingly functional subset of Python including variables, arithmetic, comparisons, control flow (if/else, while, for loops), function definitions, print statements, and indentation-based blocks.

To achieve the 1024-byte limit, Henley aggressively code-golfed the readable 4800-byte version using techniques like single-letter names, implicit variable declarations, bitwise operations, and ASCII value tricks. The interpreter cleverly handles loops and function calls by jumping backward in the source code to re-parse rather than storing intermediate representations, demonstrating that even with severe constraints, functional language interpretation is possible through creative engineering.

### Nifty Django Feature: Q() Objects - (Python Weekly)

https://www.better-simple.com/django/2026/09/09/nifty-feature-q-objects/

# Summary

This article explains Django's Q() objects, which represent SQL conditions used in database queries. Q() objects allow developers to express complex filter logic that gets translated into WHERE clauses in SQL. The key advantage is that Q() objects support logical operations (AND, OR, NOT) and can be dynamically built and composed, making them especially useful for creating flexible, reusable filter logic—such as search functionality or building filters based on user input.

The article demonstrates practical applications including simple filtering examples, dynamic query building for search terms, and composing Q() objects across different models using class methods. It also highlights an important performance consideration: when filtering across model relationships (foreign keys, many-to-many), Django automatically joins tables, and using Q() objects in a single `.filter()` call prevents unnecessary multiple joins that could occur with chained `.filter()` calls.
